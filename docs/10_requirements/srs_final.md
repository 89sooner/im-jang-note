# 임장노트 최종 요구사항 정의서

## 1. 문서 개요

- 문서명: 임장노트(ImJang Note) 최종 요구사항 정의서
- 문서 버전: v0.1
- 문서 성격: 최종 SRS 겸 구현 기준 문서 (최상위 제품 진실)
- 기준 문서: `feature.md`, `prd.md`, `workflow.md`
- 충돌 시 본 문서가 모든 하위 문서(파생 UI·기술 아키텍처·딜리버리·에이전트 브리프)에 우선한다.

## 2. 통합 결론

임장노트는 부부 2인이 하나의 공유 워크스페이스에서, 지도 위 단지를 클릭해 구조화된 임장 후기를 작성·공유·비교하는 React Native(Expo) 앱이다. 국토교통부 OpenAPI의 단지 정보·실거래가를 Supabase Edge Function 프록시로 결합하고, Supabase(Postgres/Auth/RLS/Realtime/Storage)로 실시간 공유와 데이터 격리를 제공한다. 오프라인 현장 작성과 사후 동기화, SaaS 수준의 보안·개인정보·관측을 만족해야 한다.

## 3. 제품 비전과 목표

### 3.1 제품 비전

- 현장의 주관적 인상과 객관적 시세를, 부부가 함께 신뢰할 수 있는 하나의 기록으로 남겨 주거 의사결정을 돕는다.

### 3.2 정량 목표

- 임장 1건 노트 작성 3분 이내, 2인 연결률 60% 이상, 오프라인 동기화 성공률 99% 이상, 크래시 프리 세션 99.5% 이상 (측정 기준은 `prd.md` §5).

## 4. 범위 정의

### 4.1 In Scope

- 인증·프로필, 부부 워크스페이스 생성·초대·실시간 동기화.
- 지도 단지 탐색·마커 클릭 진입·현위치.
- 단지 기본정보·실거래가 조회 및 서버 캐시.
- 임장 노트 작성/목록/수정·삭제, 구조화 체크리스트, 별점, 자유 메모, 사진 첨부, 코멘트.
- 즐겨찾기/후보, 지역/단지명 검색, 위치/개인정보 동의 관리.

### 4.2 Conditional Scope

- 멤버 권한/역할, 노트 보유 단지 시각 구분, 평형별 시세 필터, 사진 뷰어, 단지 비교, 조건 필터, 알림, 오프라인 작성·동기화, 앱 설정, 계정 탈퇴.

### 4.3 Out of Scope

- 매물 거래/중개, 공개 커뮤니티, 3인 이상 협업, 결제/구독, AI 추천. (`feature.md` §4)

## 5. 가정과 제약

### 5.1 기본 가정

1. 워크스페이스는 정원 2인(owner, partner)으로 고정한다.
2. 단지 식별은 국토부 단지 식별자 또는 좌표+주소 기반 내부 식별자로 정규화한다.
3. 동시 편집 빈도는 낮으며 충돌 정책은 ADR-005로 정의한다.

### 5.2 기술 제약

1. 클라이언트는 React Native(Expo), Android 우선.
2. 외부 API(국토부, 지도 REST) 키는 클라이언트에 노출하지 않으며 Edge Function을 경유한다.
3. 데이터 접근은 Supabase RLS로 워크스페이스 단위 격리한다.

### 5.3 보안/운영 제약

1. 위치·사진 등 민감정보는 명시 동의 후 수집하고 철회·삭제를 지원한다(PIPA).
2. 외부 API 장애 시 캐시 폴백과 저하 모드 표시를 제공한다.
3. 모든 쓰기 작업은 인증·권한 검증과 감사 로깅 대상이다.

## 6. 사용자와 권한 모델

| 사용자 유형 | 권한 | 주요 목표 |
| --- | --- | --- |
| owner | 워크스페이스 생성/삭제, 멤버 초대/제거, 모든 공유 노트 읽기·자기 노트 편집 | 후보 정리·의사결정 |
| partner | 노트 작성·코멘트, 공유 노트 읽기, 본인 노트 편집, 워크스페이스 삭제 불가 | 동행 기록·의견 |
| 비인증 | 로그인/가입 화면만 접근 | 진입 |

## 7. 대표 사용자 시나리오

## 8. 기능 실현 방식 분류

- Type A: 클라이언트 로컬/설정. Type B: Supabase·외부 API 연동. Type C: 오프라인/충돌 등 복잡 로직. Type D: 제외/후순위.

## 9. 기능 요구사항

문장 규칙: "시스템은 …해야 한다(shall)". 검증 가능하도록 트리거·반응·예외를 명시한다.

### 9.1 FR-AUTH 인증/계정

- FR-AUTH-001 시스템은 이메일 및 지원 소셜 제공자로 로그인하고 세션 토큰을 발급·자동 갱신해야 한다.
- FR-AUTH-002 시스템은 최초 로그인 시 표시명과 아바타를 포함한 사용자 프로필을 생성·수정할 수 있어야 한다.
- FR-AUTH-003 시스템은 유효 세션이 있으면 재로그인 없이 진입시키고, 만료 시 로그인 화면으로 안전하게 전환해야 한다.
- FR-AUTH-004 시스템은 로그아웃과 계정 탈퇴를 제공하고, 탈퇴 시 개인 데이터 삭제를 예약하며 워크스페이스 단독 소유 시 위임/삭제를 요구해야 한다. (Should)

### 9.2 FR-WS 워크스페이스/공유

- FR-WS-001 시스템은 사용자가 워크스페이스를 생성하면 생성자를 owner로 지정해야 한다.
- FR-WS-002 시스템은 owner가 만료 가능한 초대 링크/코드를 발급하고, 수락자를 partner로 추가하되 정원 2인을 초과하지 않아야 한다.
- FR-WS-003 시스템은 노트·코멘트·즐겨찾기 변경을 같은 워크스페이스의 다른 멤버에게 실시간(수초 내) 반영해야 한다.
- FR-WS-004 시스템은 owner/partner 역할에 따라 삭제·멤버 관리 권한을 분리 적용해야 한다. (Should)

### 9.3 FR-MAP 지도/탐색

- FR-MAP-001 시스템은 Kakao Map 위에 현재 지도 영역의 단지 마커를 표시해야 한다.
- FR-MAP-002 시스템은 줌 레벨에 따라 마커를 클러스터링해 가독성과 성능을 유지해야 한다.
- FR-MAP-003 시스템은 단지 마커 탭 시 단지 상세로 진입시키고, 미등록 단지는 좌표/주소로 신규 생성할 수 있어야 한다.
- FR-MAP-004 시스템은 위치 권한 허용 시 현위치로 이동하고 지도 패닝/검색 이동을 지원해야 한다.
- FR-MAP-005 시스템은 노트 보유·즐겨찾기 단지를 마커 상태색으로 구분해야 한다. (Should)

### 9.4 FR-DATA 단지정보/실거래가

- FR-DATA-001 시스템은 단지 상세에서 국토부 공동주택 단지 기본정보를 표시해야 한다.
- FR-DATA-002 시스템은 단지의 아파트 실거래가 목록과 시세 추이를 표시해야 한다.
- FR-DATA-003 시스템은 국토부 API 호출을 서버측에서 프록시·캐시하고, 키를 클라이언트에 노출하지 않아야 한다.
- FR-DATA-004 시스템은 전용면적/평형 구간으로 실거래가를 필터링할 수 있어야 한다. (Should)

### 9.5 FR-NOTE 임장 노트

- FR-NOTE-001 시스템은 특정 단지에 연결된 임장 노트를 생성하고 방문일·작성자를 기록해야 한다.
- FR-NOTE-002 시스템은 교통·학군·소음·채광·관리상태·주변환경 등 표준 항목의 점수와 항목별 메모를 저장해야 한다.
- FR-NOTE-003 시스템은 노트의 별점(종합 평가)을 저장하고 목록·비교에서 표시해야 한다.
- FR-NOTE-004 시스템은 자유 형식 메모를 길이 제한 내에서 저장해야 한다.
- FR-NOTE-005 시스템은 워크스페이스의 노트를 최신순/단지순으로 페이지네이션해 보여줘야 한다.
- FR-NOTE-006 시스템은 작성자 또는 owner만 노트를 수정·삭제할 수 있게 하고 삭제는 소프트 삭제로 처리해야 한다.

### 9.6 FR-MEDIA 사진

- FR-MEDIA-001 시스템은 노트에 사진을 첨부하고 썸네일을 생성하며 용량/개수 제한을 적용해야 한다.
- FR-MEDIA-002 시스템은 첨부 사진을 풀스크린 갤러리로 열람할 수 있어야 한다. (Should)

### 9.7 FR-COMMENT 코멘트

- FR-COMMENT-001 시스템은 노트에 코멘트를 작성하고 같은 워크스페이스 멤버에게 실시간 표시해야 한다.

### 9.8 FR-FAV 즐겨찾기/비교

- FR-FAV-001 시스템은 단지를 즐겨찾기/후보로 토글하고 목록으로 모아 보여줘야 한다.
- FR-FAV-002 시스템은 선택한 후보 단지들의 별점·시세·체크리스트를 비교표로 제시해야 한다. (Should)

### 9.9 FR-SEARCH 검색/필터

- FR-SEARCH-001 시스템은 지역·주소·단지명으로 단지를 검색해 지도/목록 결과를 제공해야 한다.
- FR-SEARCH-002 시스템은 가격대·평형·평점 조건으로 결과를 필터링해야 한다. (Should)

### 9.10 FR-NOTIFY 알림

- FR-NOTIFY-001 시스템은 배우자의 새 노트/코멘트 발생 시 푸시 알림을 발송해야 한다. (Should)
- FR-NOTIFY-002 시스템은 알림 센터와 알림 on/off 설정을 제공해야 한다. (Should)

### 9.11 FR-SYNC 오프라인/동기화

- FR-SYNC-001 시스템은 오프라인 상태에서 노트/사진 작성을 로컬 큐에 저장해야 한다. (Should)
- FR-SYNC-002 시스템은 온라인 복귀 시 큐를 자동 동기화하고 충돌은 ADR-005 정책으로 해소해야 한다. (Should)

### 9.12 FR-SET 설정/개인정보

- FR-SET-001 시스템은 알림·지도·언어 등 앱 설정을 저장·적용해야 한다. (Should)
- FR-SET-002 시스템은 위치/사진/개인정보 동의 상태를 표시·변경하고 철회·삭제를 지원해야 한다.

## 10. 외부 인터페이스 요구사항

- 국토교통부 OpenAPI: 공동주택 단지 기본정보, 아파트 매매 실거래가. Edge Function 프록시·캐시 경유(FR-DATA-003).
- Kakao Map: 지도 타일·마커·지오코딩. 연동 방식 ADR-003.
- Expo Push: 디바이스 토큰 등록·발송(FR-NOTIFY-001).
- Supabase: Auth, Postgres+RLS, Realtime, Storage, Edge Functions.

## 11. 데이터 및 추적성 요구사항

- 핵심 엔티티: user_profile, workspace, workspace_member, workspace_invite, complex, note, note_checklist, note_photo, comment, favorite, transaction_cache, notification, device_token (상세는 `30_technical_architecture/imjang_note_data_model.md`).
- 모든 요구사항은 `requirements_screen_traceability_matrix.md`에서 화면 ID로 추적되어야 한다.

## 12. 비기능 요구사항

### NFR-001 성능

- 지도 첫 렌더 2.5초 이내(LTE), 마커 1,000개 근접 60fps 스크롤, 온라인 노트 저장 1초 이내, 단지 상세 실거래가 표시 1.5초 이내(캐시 적중 시).

### NFR-002 보안

- Supabase Auth + RLS로 워크스페이스 격리. 외부 API 키 서버 보관. 전송 구간 TLS, 사진은 서명 URL 접근.

### NFR-003 개인정보

- 위치·사진·연락처는 동의 기반 수집, 동의 철회·계정/데이터 삭제 지원, 최소 수집·보존기간 명시(PIPA 준수).

### NFR-004 신뢰성/가용성

- 외부 API 장애 시 캐시 폴백 + "최신 아님" 저하 모드. 오프라인 작성 무손실. 월간 핵심 흐름 가용성 99.5% 목표.

### NFR-005 접근성

- 한 손 조작 동선, 최소 44pt 터치 타깃, 스크린리더 레이블, 명도 대비 WCAG AA, 동적 글자 크기 대응.

### NFR-006 운영성/관측성

- 구조화 로그·메트릭·트레이스, 크래시 리포팅, 외부 API 실패율·동기화 실패율 알림 룰, 핵심 흐름 대시보드.

### NFR-007 확장성/이식성

- 지도·데이터 공급자 어댑터 경계 유지, iOS 확장 여지, 워크스페이스 정원 확장 가능 구조(현재 2 고정).
